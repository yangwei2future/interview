# Kafka 实践手册

> 原生 Kafka Clients（非 Spring Kafka），覆盖 Producer 和 Consumer 主流程的动手实操。

## 一、Producer 主流程实践

### 1.1 确保 Kafka 集群在运行

```bash
docker ps | grep kafka
```

应该看到 kafka1、kafka2、kafka3 三个容器都是 Up 状态。

### 1.2 编译 kafka 模块

```bash
cd /Users/yangwei/IdeaProjects/interview
mvn clean compile -pl kafka
```

### 1.3 运行 Producer Demo

```bash
cd /Users/yangwei/IdeaProjects/interview/kafka
mvn exec:java -Dexec.mainClass="kafka.producer.KafkaProducerDemo"
```

### 1.4 观察输出，对照理解流程

**第一段 — 无 Key 消息（轮询分区）：**

```
[1] 发送 3 条无 Key 消息（轮询分区）---
  -> partition=0 offset=5 value=message-1
  -> partition=1 offset=3 value=message-2
  -> partition=2 offset=4 value=message-3
```

对照理解：key=null 时，Producer 用 Round-Robin 轮询分配 Partition，3 条消息散落在不同分区。

**第二段 — 同一 Key 消息（顺序保证）：**

```
[2] 同一 orderId 的三条消息（Key 路由，保证顺序）---
  key=ORDER-1001 -> partition=1 offset=4 | 创建订单
  key=ORDER-1001 -> partition=1 offset=5 | 支付成功
  key=ORDER-1001 -> partition=1 offset=6 | 开始发货
```

对照理解：三条消息的 key 相同，`hash(ORDER-1001) % 3` 结果相同，全部落到 Partition 1。同一个 Partition 内 offset 连续递增，顺序天然保证。

**第三段 — 不同 Key 消息（分区分散）：**

```
[3] 不同 Key 分散到不同分区---
  key=user-1 partition=0
  key=user-2 partition=2
  key=user-3 partition=1
  key=user-4 partition=2
  key=user-5 partition=0
```

对照理解：不同 user-* 的 hash 结果不同，消息被分散到不同 Partition，实现并行写入。

### 1.5 Producer 主流程总结

```
new KafkaProducer(properties)
       ↓
   send(record, callback)
       ↓
   序列化 Key/Value
       ↓
   分区器：hash(key) % partitionCount  →  确定目标 Partition
       ↓
   写入缓冲区 RecordAccumulator（攒批：linger.ms=5ms / batch.size=16KB）
       ↓
   Sender 线程异步发送到 Broker
       ↓
   Broker 写入 Leader Partition，Follower 同步（acks=all 等待所有副本确认）
       ↓
   回调：返回 partition + offset（或异常）
```

### 1.6 Producer 关键配置（KafkaConfig.producerProps）

| 配置 | 值 | 作用 |
|------|-----|------|
| `acks` | all | 所有副本确认才返回 |
| `retries` | 3 | 发送失败重试 |
| `enable.idempotence` | true | 幂等防重复发送 |
| `linger.ms` | 5 | 攒批等待时间 |
| `batch.size` | 16384 | 批量大小（16KB） |
| `compression.type` | lz4 | 压缩算法 |

## 二、Consumer 主流程实践

### 2.1 先让 Producer 多发一些消息（给 Consumer 准备数据）

```bash
cd /Users/yangwei/IdeaProjects/interview/kafka
mvn exec:java -Dexec.mainClass="kafka.producer.KafkaProducerDemo"
```

### 2.2 运行 Consumer Demo

```bash
mvn exec:java -Dexec.mainClass="kafka.consumer.KafkaConsumerDemo"
```

### 2.3 观察输出，对照理解流程

```
===== Kafka Consumer Demo（手动提交）=====

--- 第 1 批，拉取 20 条 ---
  partition=0 offset=0  key=null        value=message-1
  partition=1 offset=0  key=ORDER-1001  value=创建订单
  partition=2 offset=0  key=user-3      value=用户3的消息
  ...
  => offset 已提交

--- 第 2 批，拉取 8 条 ---
  partition=0 offset=20 key=null        value=message-21
  ...
  => offset 已提交
```

几个要观察的点：

1. **poll() 一次拉一批**：每批最多 `max.poll.records=20` 条，不是一条一条拉
2. **分区并行消费**：一批消息来自不同 Partition，一次 poll 返回了 Partition 0、1、2 的消息混合在一起
3. **手动提交**：每处理完一批才 `commitSync()`，处理逻辑在提交之前——这是"不丢消息"的关键

### 2.4 Consumer 主流程总结

```
new KafkaConsumer(properties)
       ↓
   subscribe(["demo-topic"])
       ↓
   poll(2s)  ← 拉一批（最多 max.poll.records=20 条）
       ↓
   for each record:
       process(record)  ← 逐条处理业务逻辑
       ↓
   commitSync()  ← 处理完一批才提交 offset
       ↓
   poll(2s)  ← 继续拉下一批
```

### 2.5 Consumer 关键配置（KafkaConfig.consumerProps）

| 配置 | 值 | 作用 |
|------|-----|------|
| `enable.auto.commit` | false | 手动提交 offset（防丢消息） |
| `auto.offset.reset` | earliest | 首次加入 Group 从最早开始消费 |
| `max.poll.records` | 20 | 每批最多拉 20 条 |
| `max.poll.interval.ms` | 300000 | poll 超时 5 分钟 |

## 三、验证"手动提交 vs 自动提交"的区别（可选）

运行 Consumer 按 `Ctrl+C` 中途强杀，再重新运行，观察：

- **手动提交模式（当前代码）**：正在处理但未提交的那批消息会重新消费（at-least-once 语义）
- 如果把 `KafkaConfig.java` 里 `ENABLE_AUTO_COMMIT_CONFIG` 改成 `"true"`，自动提交模式下，消息拉下来 5 秒就自动提交——不管你是否处理完

## 四、Topic 分区管理

### 4.1 自动创建 Topic（开发环境）

Kafka 默认 `auto.create.topics.enable=true`，Producer 往不存在的 Topic 发消息时 Broker 会自动创建，但**默认只有 1 个分区**。

开发时方便，生产环境必须关掉这个开关，Topic 由管理员提前规划好分区数和副本数再手动创建。

### 4.2 查看 Topic 分区信息

```bash
# 查看所有 Topic
docker exec kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:29092 --describe
```

输出关注两列：
- `PartitionCount`：总分区数
- `Leader` / `Replicas` / `Isr`：每个分区的分布情况

### 4.3 扩分区（生产积压时的应急操作）

```bash
docker exec kafka1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:29092 \
  --alter --topic demo-topic --partitions 6
```

**只能扩不能缩**——`--partitions` 只接受比当前值大的数字。

### 4.4 扩分区的三重副作用

```
扩分区（3 → 6）
  ├── 1. 触发 Rebalance → 整个 Consumer Group 暂停消费（STW），可能短期加剧积压
  ├── 2. Key 路由漂移 → hash(key)%3 ≠ hash(key)%6，同 Key 消息可能落到不同分区，顺序被打乱
  └── 3. 老数据不移动 → 新分区只接新消息，老分区里的积压还得靠老 Consumer 消化
```

这就是为什么生产上强调**分区数要提前规划好，不要随便扩**——它救急可以，但代价不小。

### 4.5 扩分区后的操作流程

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1. 扩分区 | `--alter --partitions N` | 瞬间完成，不移动已有数据 |
| 2. 扩 Consumer | 加到和分区数一致 | 新 Consumer 接管新分区的消息 |
| 3. 验证 | `--describe --group xxx` 看 LAG | 确认积压是否下降 |
