# 垃圾回收器详解

## 演进路线

```
                    时间线
    ┌──────┐  ┌──────┐  ┌───────────┐  ┌──────┐  ┌──────────────┐  ┌──────┐
    │Serial│→│ParNew│→│ Parallel   │→│ CMS  │→│      G1      │→│ ZGC  │
    └──────┘  └──────┘  │ Scavenge  │  └──────┘  └──────────────┘  └──────┘
                        └───────────┘                │
                                                ┌────┴────┐
                                                │Shenandoah│
                                                └─────────┘
JDK 1.3     1.4        1.4+            1.5     7(default)      11/15+
                        新生代/老年代配对关系
                        ═══════════════

   新生代                      老年代
   ─────────────────────────────────
   Serial          ←→       Serial Old      (单线程组合)
   ParNew          ←→       CMS             (低延迟组合)
   Parallel Scavenge ←→    Parallel Old     (高吞吐组合)
   G1、ZGC、Shenandoah 不分工，全堆通吃
```

---

## 一、Serial / Serial Old

### Serial（新生代）

**特点：** 单线程，做垃圾回收时所有用户线程必须停止（STW）。

```
┌─ 用户线程 ─┐           ┌─ STW ─┐           ┌─ 用户线程 ─┐
│  ● ● ● ● ● │  ──▶     │  GC   │    ──▶    │  ● ● ● ● ● │
└────────────┘           └───────┘           └────────────┘
```

| 项目 | 说明 |
|------|------|
| 作用区域 | 新生代 |
| 算法 | 复制（Eden → S0/S1 来回倒） |
| 线程数 | 1 条 GC 线程 |
| STW | 有，而且全程 |
| 适用 | 桌面应用、客户端（`-client` 模式默认） |

**优势：** 单线程没有线程切换开销，小堆（<100MB）下效率反而最高，"船小好调头"。

### Serial Old（老年代）

与 Serial 配对的老年代收集器，算法用**标记-整理**，同样是单线程。

**兜底角色：** 当 CMS 出现 Concurrent Mode Failure 时，会退化成 Serial Old 做一次 Full GC，此时 STW 极长（老年代越大越久）。

**参数：**
```bash
-XX:+UseSerialGC   # 同时启用 Serial + Serial Old
```

---

## 二、ParNew

**本质：Serial 的多线程版本。**

| 项目 | 说明 |
|------|------|
| 作用区域 | 新生代 |
| 算法 | 复制 |
| 线程数 | 多条 GC 线程并行（`-XX:ParallelGCThreads`） |
| STW | 有，但多线程并行更短 |
| 配合对象 | **CMS**（CMS 只收老年代，ParNew 收新生代） |

```
Serial 单线程：               ParNew 多线程：
    STW 期                      STW 期
   ┌──────┐                  ┌──────┐
   │  GC  │                  │ GC GC │
   └──────┘                  │ GC GC │
                              └──────┘
```

> **为什么 CMS 必须配 ParNew？** CMS 和 Parallel Scavenge 的底层框架不同，无法搭配；同时 CMS 需要 ParNew 的多线程能力来缩短新生代 GC 的 STW 时间。

## 三、Parallel Scavenge / Parallel Old（JDK 8 默认）

**目标：吞吐量优先。** 单位时间内，用户代码运行时间占比最高。

```
吞吐量 = 运行用户代码时间 / (运行用户代码时间 + GC 时间)

例：GC 花了 1 秒，用户代码跑了 99 秒 → 吞吐量 = 99%
```

| 项目 | Parallel Scavenge | Parallel Old |
|------|-------------------|--------------|
| 作用区域 | 新生代 | 老年代 |
| 算法 | 复制 | 标记-整理 |
| 线程数 | 多线程 | 多线程 |
| 默认 | **JDK 8 默认 GC 组合** | |

### 和 ParNew 的区别

ParNew 关注**减少 GC 停顿时间**，Parallel 关注**提高总体吞吐量**。方向不同：

- ParNew：停顿短，但 GC 总耗时可能更多（GC 频率更高）
- Parallel：停顿可能更长，但 GC 总耗时少，省下的时间都给用户线程跑业务

### 自适应调节

Parallel 有独有的 **自适应调节策略**，打开后只需设 `-XX:MaxGCPauseMillis` 和 `-XX:GCTimeRatio`，JVM 自动调：
- `-XX:+UseAdaptiveSizePolicy`：自动调整新生代大小、Eden/Survivor 比例、晋升年龄阈值
- 适合懒人调优：告诉它你的目标，它自己动手调参数

**参数：**
```bash
-XX:+UseParallelGC        # 新生代 Parallel Scavenge + 老年代 Serial Old（不推荐）
-XX:+UseParallelOldGC     # 新生代 Parallel Scavenge + 老年代 Parallel Old
-XX:MaxGCPauseMillis=200  # 目标停顿时间
-XX:GCTimeRatio=99        # GC 时间占比 1/(1+99) = 1%
```

## 四、CMS（Concurrent Mark Sweep）

**目标：最短停顿时间。** 让 GC 线程和用户线程尽可能同时工作。

### 工作原理

CMS 只负责老年代，新生代交给 ParNew。

```
老年代回收四个阶段：

① 初始标记 (STW)        ② 并发标记 (无STW)       ③ 重新标记 (STW)        ④ 并发清除 (无STW)
    ┌─────┐                ┌──────────────┐          ┌───────┐               ┌──────────────┐
    │标记  │                │ GC    ● ● ●  │          │修正漏标│               │ 清除  ● ● ●  │
    │Roots │                │标记  用户线程  │          │       │               │ 垃圾  用户线程 │
    └─────┘                └──────────────┘          └───────┘               └──────────────┘
         ↓                        ↓                       ↓                        ↓
    标记 GC Roots            和用户线程              修正并发标记              和用户线程
    直接引用的对象            同时遍历对象图            期间的漏标              同时回收垃圾
```

### 各阶段详解

**① 初始标记（STW，极短）：** 从 GC Roots 出发，只标记它们**直接**关联的对象。不遍历对象图，所以极短。

> **为什么初始标记必须 STW？** 需要固定 GC Roots 这个起点——起点不稳，并发标记结果不可信。

**② 并发标记（无 STW，长）：** 和用户线程同时跑，从初始标记的对象开始遍历整个对象图。持续时间最长，但用户无感知。

**③ 重新标记（STW，中等）：** 修正并发标记期间的"漏标"。并发标记时用户线程可能修改引用关系，写屏障记录这些变化，重新标记阶段补上。

```
漏标场景：
  并发标记期间，用户线程把"B→C"改成"A→C"
  此时 C 已经被标记过，但 B 还没被扫到
  → C 可能被遗漏
  → 写屏障记录这次修改
  → 重新标记阶段补标 C
```

- **漏标**：并发标记后引用关系变化，有存活对象被误认为垃圾（不回收则下次再收，还能接受）
- **错标（浮动垃圾）**：并发标记期间已标记存活的对象引用后来被断开，变成垃圾但这次不回收，留到下次 GC

> CMS 采用**增量更新（Incremental Update）**来解决漏标——当对象的引用被修改时，把该对象记录起来，重新标记阶段重新扫描。

**④ 并发清除（无 STW，长）：** 和用户线程同时跑，清除未标记对象。在此期间产生的新垃圾（浮动垃圾）本次不回收。

### CMS 的三个致命缺陷

**1. 内存碎片（最致命）：**

CMS 用标记-清除，不整理内存。碎片持续积累，当一个大对象找不到连续空间时：
```
总空闲 = 500MB，但没有一块连续的 10MB
→ 触发 Concurrent Mode Failure
→ 回退到 Serial Old 单线程整理
→ STW 时间 = 整个老年代的标记整理时间（可能几十秒）
```

**2. 浮动垃圾：**

并发清除期间，用户线程产生的新垃圾本次收不掉。CMS 需要预留空间给这些浮动垃圾——老年代使用率达到一定阈值就触发并发标记，不能在满了再动手。

```bash
-XX:CMSInitiatingOccupancyFraction=70  # 老年代到 70% 就触发 GC（默认 92）
```

如果留的空间不够，用户线程分配内存失败 → Concurrent Mode Failure → Serial Old 兜底。

**3. 抢占 CPU 资源：**

并发标记和并发清除阶段，GC 线程要跑，会和用户线程抢 CPU。CPU 核数不够时（<4核），吞吐量下降明显。

```
用户线程 100% → GC 线程上来就变成 60-70% 的有效吞吐
```

### 参数汇总

```bash
-XX:+UseConcMarkSweepGC
-XX:+UseParNewGC                        # CMS 必须配 ParNew
-XX:CMSInitiatingOccupancyFraction=70   # 老年代到 70% 触发 GC
-XX:+UseCMSCompactAtFullCollection      # Full GC 后做一次碎片整理
-XX:CMSFullGCsBeforeCompaction=5        # 每 5 次 Full GC 后整理一次
```

### 已废弃

JDK 9 标记废弃（deprecated），JDK 14 彻底移除。原因：碎片问题无解、G1 已经成熟。

## 五、G1（Garbage First）

**JDK 9+ 默认 GC，目标是"可预测的停顿时间"。**

### 核心设计：Region

G1 打破固定分代边界，把堆切成大小相同的 **Region**（1~32MB）：

```
┌────┬────┬────┬────┬────┬────┬────┐
│ E  │ S  │ O  │ E  │ H  │ O  │ E  │   E = Eden Region
├────┼────┼────┼────┼────┼────┼────┤   S = Survivor Region
│ O  │ E  │ O  │ S  │ E  │ O  │ E  │   O = Old Region
├────┼────┼────┼────┼────┼────┼────┤   H = Humongous（大对象专用）
│ E  │ O  │ E  │ O  │ H  │ E  │ S  │
└────┴────┴────┴────┴────┴────┴────┘
```

- Region 角色动态分配，不固定
- Humongous Region：超过单个 Region 一半大小的对象，直接分配连续多个 Region 存放
- 每个 Region 物理不连续，逻辑连续

### Young GC（新生代回收）

Eden Region 满了触发，STW，多线程并行复制：

```
回收前：                         回收后：
E E E S S (满了)               [空] [空] S' O O
                        复制存活 → 新 Survivor / 老年代
                        直接清空原 Region
```

### Mixed GC（混合回收，G1 独有）

老年代占堆超过 **IHOP**（默认 45%）时触发。回收全部新生代 Region + **部分**老年代 Region（挑垃圾最多的）。

```
垃圾最多的 Region 优先回收 → 所以叫 "Garbage First"
```

> 为什么不全量回收老年代？控制 STW 时间——只回收性价比最高的那些 Region 就够了。

**Mixed GC 四个阶段：**

```
① 初始标记  → STW，和 Young GC 一起做（省一次 STW）
② 并发标记  → 不 STW，遍历整个堆的对象图
③ 最终标记  → STW，修正漏标（G1 用 SATB 算法）
④ 筛选回收  → STW，按垃圾量排序，只回收最有价值的 Region
```

**SATB（Snapshot-At-The-Beginning）算法：**

CMS 用增量更新处理漏标，G1 用 SATB。核心思想：**在并发标记开始前给对象图拍快照**，并发标记期间删掉的对象按"存活"处理（变成浮动垃圾，下次收）。

```
CMS 增量更新：关注"新增的引用" → 写屏障记录被修改的对象
G1 SATB：    关注"删除的引用" → 写屏障记录被删除引用前的值
```

### G1 可预测停顿的核心

设置 `-XX:MaxGCPauseMillis=200`，G1 根据历史数据估算每个 Region 的回收耗时，按目标时间反算这次能回收多少 Region：

```
目标暂停 200ms → 每个 Region 平均回收 5ms → 这次最多回收 40 个 Region
```

这是一个**软目标**，G1 尽力满足但不保证。

### Full GC 触发条件

G1 也有 Full GC（回退为 Serial 单线程全堆回收，STW 极长）：

- 晋升老年代的对象太多，Mixed GC 来不及回收
- 大对象分配找不到连续 Humongous Region
- 并发标记期间老年代被填满

排查：`jstat` 看到 FGC 列在增长，说明 G1 扛不住了，需要调参数或加内存。

### 参数

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200              # 目标停顿时间（软目标）
-XX:G1HeapRegionSize=4m               # Region 大小，堆 4-8G 建议 4m
-XX:InitiatingHeapOccupancyPercent=45 # 老年代占比达 45% 触发 Mixed GC
-XX:G1ReservePercent=10               # 预留 10% 给晋升的对象
-XX:G1NewSizePercent=5                # 年轻代最小占比
-XX:G1MaxNewSizePercent=60            # 年轻代最大占比
-XX:ParallelGCThreads=8               # GC 并行线程数
-XX:ConcGCThreads=2                   # 并发标记线程数（约并行线程的 1/4）
```

## 六、ZGC（Z Garbage Collector）

**JDK 11 实验性引入，JDK 15 生产可用。目标：超低延迟（<1ms）。**

### 核心设计：染色指针（Colored Pointers）

ZGC 在 64 位指针上做文章，利用指针里的空闲 bit 存储 GC 状态信息：

```
64 位指针在 ZGC 中的布局：

┌──────┬──────┬──────────┬──────────────────────────────┐
│ 18位  │ 4位  │  42位     │         （实际寻址用低 42 位）  │
│ 保留  │染色位 │  地址     │                                │
└──────┴──────┴──────────┴──────────────────────────────┘
               │
     ┌────────┼────────┬────────┐
   Finalizable  Remapped  Marked1  Marked0
```

染色指针的好处：
- 不需要额外内存记录 GC 状态（状态信息编码在指针里）
- 读屏障检查指针颜色，发现"过期"指针时自动修复指向最新对象
- 染色指针 + 读屏障 = 并发移动对象不掉链

### ZGC 的核心流程

```
① 初始标记  → STW，极短（<1ms），只标 GC Roots
② 并发标记  → 不 STW，遍历对象图
③ 最终标记  → STW，极短
④ 并发整理  → 不 STW，移动对象 + 重映射（ZGC 最厉害的地方）
```

**并发整理怎么做到不 STW？** 读屏障。移动对象时，用户线程读取对象会触发读屏障，读屏障发现"这个对象搬家了"就自动找新地址返回。整个过程用户线程不停工。

### 特点

| 项目 | 说明 |
|------|------|
| 算法 | 染色指针 + 读屏障 |
| STW 时间 | <1ms（不管堆多大） |
| 堆大小 | 支持 TB 级 |
| 分代 | JDK 21 引入分代 ZGC（降低年轻人开销） |
| 代价 | 吞吐量比 G1 低约 10-15% |

### 参数

```bash
-XX:+UseZGC
-Xmx16g                     # ZGC 推荐大堆
-XX:ConcGCThreads=4         # 并发线程数
```

## 七、Shenandoah

Red Hat 开发，捐给 OpenJDK，JDK 12 引入。和 ZGC 目标一样：**超低延迟**。

| 对比 | ZGC | Shenandoah |
|------|-----|------------|
| 核心技术 | 染色指针 | 转发指针（Brooks Pointer） |
| 并发整理 | 读屏障 + 染色指针 | 读屏障 + 转发指针 |
| 平台 | Linux 首选 | 跨平台 |
| JDK 版本 | 11 实验，15 生产 | 12 引入，15 生产 |

转发指针：每个对象头前面加一个指针，指回自己。移动对象后把旧地址的转发指针指向新地址，读屏障读到旧地址自动跳转。

## 八、Epsilon（No-Op GC）

**只分配，不回收。** JDK 11 引入，用于性能测试、代码性能基准测量。

```bash
-XX:+UseEpsilonGC
```

用处：
- 测试 GC 对性能的影响（隔离 GC 开销）
- 短生命周期应用：跑一会儿就退出，没必要做 GC

## 九、垃圾收集器快速选型

```
                    开始
                     │
              ┌──────▼──────┐
              │ 堆 < 100MB？ │──是──▶ Serial
              └──────┬──────┘
                     │否
              ┌──────▼──────┐
              │ 关注吞吐量？ │──是──▶ Parallel
              └──────┬──────┘
                     │否（关注延迟）
              ┌──────▼──────┐
              │ 停顿 < 1ms？│──是──┬▶ ZGC（大堆 / Linux）
              └──────┬──────┘      └▶ Shenandoah（跨平台）
                     │否（可接受几十ms）
              ┌──────▼──────┐
              │ 停顿 < 200ms│──是──▶ G1
              └──────────────┘
```

| 场景 | 推荐 GC | 原因 |
|------|---------|------|
| 桌面应用、小内存 | Serial | 小堆下单线程最快 |
| 后台计算、批处理 | Parallel | 吞吐量最高 |
| 线上接口服务（4G+） | G1 | 可预测停顿，JDK9+ 默认 |
| 低延迟交易、游戏服务器 | ZGC | STW < 1ms |
| Kafka、ES 等堆外大户 | G1/ZGC | 大堆友好 |

> JDK 9 起 G1 为默认，JDK 14 移除 CMS，新项目不要再选 CMS。

## 十、收集器对比速记表

| 收集器 | 代别 | 算法 | 线程 | STW | 目标 | 状态 |
|--------|------|------|------|-----|------|------|
| Serial | 新生代 | 复制 | 单 | 全部 | 客户端 | 存活 |
| Serial Old | 老年代 | 标记-整理 | 单 | 全部 | 兜底/CMS 后备 | 存活 |
| ParNew | 新生代 | 复制 | 多 | 全部 | 配合 CMS | 存活 |
| Parallel Scavenge | 新生代 | 复制 | 多 | 全部 | 吞吐量 | JDK8 默认新生代 |
| Parallel Old | 老年代 | 标记-整理 | 多 | 全部 | 吞吐量 | JDK8 默认老年代 |
| CMS | 老年代 | 标记-清除 | 多 | 部分 | 低延迟 | **JDK14 已移除** |
| G1 | 全堆 | 复制+标记整理 | 多 | 部分 | 可预测停顿 | JDK9+ 默认 |
| ZGC | 全堆 | 染色指针 | 多 | <1ms | 超低延迟 | JDK15 生产可用 |
| Shenandoah | 全堆 | 转发指针 | 多 | <1ms | 超低延迟 | JDK15 生产可用 |
| Epsilon | - | 无 | - | 无 | 测试/基准 | JDK11 引入 |
