# Harness Engineering 完整笔记

## 一、核心认知

### 1.1 什么是 Harness Engineering

```
Harness = 马具、缰绳
         ↓ 引申
AI 模型的"驾驭系统"：规则、工具、任务、测试、架构 的有机组合
         ↓ 目标
让 AI 从"能写代码" → "能稳定完成完整工程任务"
```

**一句话定义：** Harness Engineering 是围绕 AI 模型构建的一套完整工作环境与流程体系，决定了你能把 AI 用到什么程度。

### 1.2 为什么 Harness 比模型更重要

| 维度 | 模型本身 | Harness 体系 |
|------|---------|-------------|
| 代码输出 | 单文件、一次性 | 多文件、可迭代、可回滚 |
| 质量保障 | 靠 prompt 约束 | Linter + 测试 + Hooks 自动化 |
| 上下文 | 单次对话 | 文档体系 + 分阶段加载 |
| 协作 | 单人使用 | SubAgents 并行 + 代码互审 |
| 可靠性 | 看运气 | 流程化、可复现 |

> **行业共识：AI 编程的瓶颈不在模型能力，而在 Harness 工程化程度。**

### 1.3 三个发展阶段

```
提示词工程（Prompt Engineering）
  → 关注"怎么问"，单轮对话优化
  → 局限：对话一长就失控，复杂任务搞不定

上下文工程（Context Engineering）
  → 关注"给什么信息"，多轮对话管理
  → 局限：缺乏执行力和质量闭环

Harness Engineering（当前阶段）
  → 关注"怎么搭建工作环境"，端到端流程管理
  → 核心：工具链 + 任务编排 + 反馈闭环 + 架构护栏
```

### 1.4 核心公式

```
Agent = 模型 + Harness

模型 = 大脑（推理能力）
Harness = 身体 + 工具 + 流程（执行能力）

大脑再聪明，没有身体也干不了活。
```

## 二、五大核心能力

### 2.1 上下文架构（Context Architecture）

#### 核心原则：按需加载，避免上下文溢出

```
传统做法（反模式）：
  一个 AGENTS.md 写 500 行 → 每次对话全量加载 → 上下文爆炸

正确做法（分层加载）：
  AGENTS.md（100 行摘要 + 索引）
    ├── 引用 → docs/frontend-guide.md（需要改前端时才加载）
    ├── 引用 → docs/security-guide.md（需要安全审查时才加载）
    └── 引用 → docs/api-design.md（需要设计接口时才加载）
```

#### 上下文架构设计四步法

**第一步：写 AGENTS.md 摘要层（~100 行）**
- 项目一句话描述
- 技术栈概览
- 目录结构地图
- 指向详细文档的索引

**第二步：分文档存储详细规范**
- 按领域拆分：`frontend.md`、`backend.md`、`database.md`、`security.md`
- 每个文档只写一个领域，控制在 200 行以内

**第三步：对话中按需加载**
- 开发前端功能 → 只加载 `frontend.md`
- 安全审查 → 只加载 `security.md`

**第四步：持续维护**
- 每次功能变化同步更新文档
- 删除过时信息，保持文档瘦身

#### 上下文大小与效果关系

| 上下文使用率 | AI 表现 | 建议 |
|-------------|---------|------|
| < 30% | 信息不足，频繁猜测 | 补充关键规范 |
| 30% ~ 60% | **最佳区间** | 保持 |
| 60% ~ 80% | 注意力稀释，遗漏细节 | 精简或拆分对话 |
| > 80% | 严重退化，胡言乱语 | 必须拆分任务 |

> **关键认知：给 AI 的信息不是越多越好，精准 > 全面。**

### 2.2 执行能力（Execution Capability）

#### 三层执行能力模型

```
Layer 1: 基础工具（内置）
  ├── 终端命令（编译、运行、Git）
  ├── 文件系统（读、写、搜索）
  └── 浏览器（查看页面、调试 UI）

Layer 2: MCP 扩展（按需接入）
  ├── 数据库查询（PostgreSQL、MySQL）
  ├── 联网搜索（查最新文档、API 变更）
  ├── 网页抓取（爬取参考页面）
  └── 外部服务（Jira、Slack、Linear）

Layer 3: Agent Skills（封装专业工作流）
  ├── 代码审查 Skill
  ├── PDF 处理 Skill
  ├── 安全扫描 Skill
  └── 自定义业务 Skill
```

#### MCP（Model Context Protocol）接入示例

```json
// .claude/mcp.json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@anthropic/mcp-playwright"]
    },
    "context7": {
      "command": "npx",
      "args": ["@anthropic/mcp-context7"]
    }
  }
}
```

接入后，AI 可以：
- `playwright` → 自动打开浏览器测试页面功能
- `context7` → 自动查最新版框架文档，不用手动复制粘贴

#### 工具选择决策树

```
需要做什么？
  ├── 读写本地文件     → 直接用内置工具
  ├── 查最新文档/API   → 配置 MCP 联网搜索
  ├── 测试前端页面     → 配置 MCP 浏览器
  ├── 查数据库         → 配置 MCP 数据库连接
  └── 重复性专业流程   → 封装为 Skill
```

> **原则：能用工具自动化的，不要让 AI 凭记忆猜。**

### 2.3 任务编排（Task Orchestration）

#### 大任务拆解策略

```
复杂需求："开发一个用户管理系统"
  ↓ 拆解
  ├── 任务1：数据库表设计（DDL + 索引）
  ├── 任务2：Entity + Repository 层
  ├── 任务3：Service 业务层
  ├── 任务4：Controller 接口层
  ├── 任务5：单元测试
  └── 任务6：集成测试
```

#### 拆解粒度标准

| 太粗 | 合适 | 太细 |
|------|------|------|
| "实现整个用户模块" | "实现用户注册 Service" | "写 UserService 第 3 行" |
| AI 容易遗漏 | 一个对话完成 | 过度拆分，沟通成本高 |
| 输出不可控 | 可验收 | 没必要 |

> **标准：一个任务 = 一个对话能完成 + 一个明确的验收标准。**

#### Plan Mode 工作流

```
第1步：需求澄清
  "我要做一个 xxx 功能，核心需求是..."
  AI：追问边界条件，输出需求确认清单

第2步：方案设计
  AI：输出技术方案（架构图 + 技术选型 + 文件清单）
  你：审查方案，确认或修改

第3步：任务拆解
  AI：将方案拆解为 Task-1、Task-2、Task-3...
  你：排优先级

第4步：逐步实现
  AI：逐任务实现，每个任务完成后验收

第5步：整体验收
  AI：运行测试 + 自测 + 回归检查
```

> **核心原则：先出方案，确认后再写代码。方案写错了改 5 分钟，代码写错了改 2 小时。**

#### SubAgents 并行模式

```
主对话（编排层）
  ├── SubAgent-A：开发订单模块     ─┐
  ├── SubAgent-B：开发支付模块     ─┤ 并行执行
  └── SubAgent-C：写单元测试       ─┘

适用条件：
  ✅ 任务之间无依赖
  ✅ 各自修改的文件不冲突
  ✅ 每个任务有独立的验收标准

不适用：
  ❌ B 模块依赖 A 模块的接口定义
  ❌ 需要修改同一批文件
```

#### 功能迭代的存档策略

```
每个功能完成后：
  1. 功能说明 → 写回对应文档
  2. 代码变更 → Git commit
  3. 关闭当前对话 → 新开对话继续下一个功能

为什么关对话？
  当前对话的上下文已经很长
  → 继续加功能会让 AI 表现下降
  → 新对话 + 关联文档 = 干净上下文 = 更好的输出质量
```

### 2.4 反馈机制（Feedback Loop）

#### 四层反馈体系

```
第1层：自动检查（最快的反馈）
  ├── Linter（代码规范）
  ├── 编译检查（类型错误）
  └── 自动化测试（功能回归）
  特点：秒级反馈，无需人工介入

第2层：报错分析与自主修复
  运行时抛异常
    → AI 读取报错信息
    → 分析根因
    → 自动修复代码
    → 重新验证
  特点：分钟级反馈，AI 自闭环

第3层：人工介入纠偏
  AI 方向跑偏、理解错误、方案不合理
    → 人在对话中指出
    → AI 调整方向
  特点：关键节点介入，防止跑偏太远

第4层：多 Agent 代码互审
  Agent-A 写代码 → Agent-B 审查
  审查维度：逻辑正确性、安全性、性能、可维护性
  特点：AI 互审，降低人的审查负担
```

#### 反馈效率对比

| 反馈方式 | 延迟 | 发现问题类型 | 成本 |
|---------|------|-------------|------|
| Linter | 秒级 | 语法、风格 | 零 |
| 编译检查 | 秒级 | 类型错误 | 零 |
| 单元测试 | 秒~分钟 | 逻辑回归 | 低 |
| AI 自主修复 | 分钟 | 运行时异常 | 低 |
| 人工审查 | 小时~天 | 架构、业务逻辑 | 高 |
| AI 互审 | 分钟 | 代码质量 | 低 |

> **原则：能自动化的反馈，不要等到人工审查才发现。**

### 2.5 架构护栏（Architecture Guardrails）

#### 五道护栏

```
第1道：专用 Linter（架构约束）
  例：禁止 Controller 直接调用 DAO
  例：禁止循环依赖
  例：API 返回值必须用统一响应体
  工具：ArchUnit（Java）、eslint-plugin-custom（JS）

第2道：Pre-commit Hooks（提交前检查）
  ├── 代码格式化
  ├── Linter 检查
  ├── 单元测试（仅变更相关）
  └── 敏感信息扫描（防止密码、密钥提交）

第3道：CI/CD 流水线（合入前检查）
  ├── 全量单元测试
  ├── 集成测试
  ├── 安全扫描
  └── 构建验证

第4道：代码垃圾回收
  定期清理：
  ├── 未使用的依赖
  ├── 死代码
  ├── 过时的注释
  └── 临时方案（workaround）→ 正规方案

第5道：Git 版本控制
  每次变更独立 commit
  → 出问题随时回滚
  → 不要在一个 commit 里混 10 个不相关的改动
```

#### 护栏力度选择

```
太松（没有护栏）
  → AI 随意发挥 → 架构快速腐化

太紧（过度约束）
  → AI 寸步难行 → 开发效率极低

合适的力度：
  → 约束关键架构决策（分层、依赖方向、API 规范）
  → 放开实现细节（变量命名、函数拆分、算法选择）
```

## 三、实战项目：万能视频下载总结器

### 3.1 全流程时间线

```
方案设计（1 天）
  ├── 明确技术栈与核心方案
  ├── Plan Mode 生成方案
  └── 人工审查确认

编码开发（2-3 天）
  ├── 配置 MCP 联网查文档
  ├── 先做核心流程（MVP）
  ├── 功能完成 → 文档沉淀 + Git 提交
  └── 新开对话 + 关联文档，保持上下文干净

测试验证（1-2 天）
  ├── AI 浏览器自动化自测
  ├── 人工提供报错信息辅助修复
  └── 用模拟数据快速验证

功能扩展（迭代）
  ├── SubAgents 并行开发独立需求
  ├── 每完成一个功能 → 提交 + 更新文档
  └── 复用上下文做 SEO/GEO 优化
```

### 3.2 各阶段关键决策

#### 方案设计阶段

```
核心原则：约束 AI 先做最小可用版本

错误做法：
  "帮我做一个万能视频下载总结器，支持 YouTube/B站/抖音，
   要能下载、转文字、翻译、生成摘要、导出 Markdown..."
  → AI 会一次性生成 2000 行代码，到处都是 bug

正确做法：
  "先做一个 YouTube 视频下载功能，能下载 MP4 就行"
  → 验证通过后，再逐个加：字幕提取 → 翻译 → 摘要 → 多平台
```

#### 编码开发阶段

```
对话管理策略：

对话-1（YouTube 下载）：
  上下文：AGENTS.md + docs/video-download.md
  产出：下载核心代码 + Git commit

对话-2（字幕提取）：
  上下文：AGENTS.md + docs/video-download.md（已更新）
  产出：字幕功能 + Git commit

对话-3（翻译集成）：
  上下文：AGENTS.md + docs/video-download.md（已更新）
  产出：翻译功能 + Git commit

每个对话干净启动，不携带历史包袱
```

#### 测试验证阶段

```
AI 自测流程：

1. AI 启动浏览器（MCP Playwright）
2. 打开应用页面
3. 输入测试 URL
4. 点击下载按钮
5. 验证文件生成
6. 如果报错 → AI 读错误信息 → 自主修复 → 重新测试
7. 如果成功 → 记录测试结果

人工介入时机：
  AI 修复 3 次还不行 → 人介入分析
  功能表现不符合预期（不是 bug，是理解偏差）→ 人纠偏
```

### 3.3 关键教训

| 教训 | 说明 |
|------|------|
| 不要一次性提大需求 | AI 输出质量与任务粒度成反比 |
| 每个功能完成就存档 | commit + 文档 + 关对话，三位一体 |
| MCP 工具提前配置好 | 不要让 AI 凭记忆写代码，让它查最新文档 |
| 人工确认关键方案 | Plan Mode 花 5 分钟确认，省 2 小时改代码 |
| SubAgents 要任务独立 | 有依赖的不能并行，强行并行只会互相踩脚 |

## 四、快速上手方法

### 4.1 五步启动法

```
项目前 → 编写 AGENTS.md 明确规则
  花 30 分钟写好，后续每次对话都受益

开发前 → AI 出方案 → 人工确认 → 再编码
  方案确认是投入产出比最高的环节

开发中 → 用 MCP/Skills 配置工具
  联网查文档、浏览器测试、数据库查询

开发后 → AI 自测验证功能
  浏览器自测 + 单元测试 + 报错自修复

迭代中 → 功能完成沉淀文档 + Git 存档
  不存档 = 白做，下次还得从头来
```

### 4.2 AGENTS.md 最小模板

```markdown
# Project Overview
[一句话描述项目]

## Tech Stack
- 后端：Java 17 + Spring Boot 3.x
- 前端：React 18 + TypeScript
- 数据库：PostgreSQL 14
- 缓存：Redis 7

## Directory Structure
src/
├── main/java/com/xxx/  → 业务代码
├── test/               → 测试代码
└── docs/               → 详细规范文档

## Key Rules
1. Controller 不能直接调用 DAO，必须经过 Service
2. API 返回统一用 Result<T> 包装
3. 数据库操作必须加事务注解

## Docs Index
- [前端规范](docs/frontend.md)
- [后端规范](docs/backend.md)
- [数据库规范](docs/database.md)
- [安全规范](docs/security.md)
```

### 4.3 常见陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| AGENTS.md 过大 | 写了 500+ 行，每次全部加载 | 拆分为摘要 + 索引 |
| 跳过方案直接写代码 | 写到一半发现方向错了 | 强制 Plan Mode 先出方案 |
| 一个对话塞太多任务 | 对话越来越长，AI 质量持续下降 | 功能完成就关对话重开 |
| 测试全靠人 | 每次改动都等人验证，效率极低 | 配置自动化测试 + AI 自测 |
| SubAgents 滥用 | 什么任务都并行，文件冲突不断 | 只在任务独立时并行 |
| 不做文档沉淀 | 代码写了但不知道为什么这么写 | 功能完成即刻更新文档 |

## 五、辅助工具

### 5.1 工具对比

| 工具 | 定位 | 核心能力 | 适合阶段 |
|------|------|---------|---------|
| **Spec Kit** | SDD 规范驱动开发 | 需求拆解 + 阶段验收 | 需求→方案 |
| **Superpowers** | 开发工作流增强 | TDD + 代码审查 + 子代理 | 编码→测试 |
| **Plan Mode** | 方案设计 | 先出方案再编码 | 方案确认 |
| **SubAgents** | 任务并行 | 独立任务同时推进 | 功能扩展 |
| **MCP** | 工具扩展 | 联网/数据库/浏览器 | 全流程 |
| **Skills** | 工作流封装 | 专业流程复用 | 重复性任务 |

### 5.2 工具选择指南

```
需求分析阶段：
  复杂需求 → Spec Kit（结构化拆解）
  简单需求 → Plan Mode（直接出方案）

编码阶段：
  大型项目 → Spec Kit + Superpowers
  中型项目 → Plan Mode + Skills
  小型改动 → 直接对话

测试阶段：
  前端项目 → MCP Playwright（浏览器自测）
  后端项目 → 自动化测试 + AI 报错自修复

维护阶段：
  定期代码审查 → Superpowers 代码审查
  技术债清理 → 代码垃圾回收流程
```

## 六、核心总结

### 6.1 三个核心转变

```
转变1：重心从"写代码"转向"做设计"
  以前：80% 时间写代码，20% 时间想方案
  现在：20% 时间写代码，80% 时间想方案 + 审查

转变2：身份从"执行者"转向"编排者"
  以前：自己一行行写代码
  现在：拆任务 → 分配 AI → 审查结果 → 合并

转变3：能力从"编码能力"转向"工程能力"
  以前：比谁代码写得快
  现在：比谁能把需求讲清楚、方案设计好、质量把控住
```

### 6.2 一句话总结

> **Harness 不是新技术，是传统工程经验在 AI 时代的重新应用。工程能力越强，越能驾驭 AI。**

### 6.3 能力成长路径

```
Level 1：能用 AI 写单个函数
  → 掌握了基本 prompt

Level 2：能用 AI 写完整模块
  → 掌握了上下文管理 + 任务拆解

Level 3：能用 AI 完成整个项目
  → 掌握了 Harness Engineering 全套

Level 4：能编排多个 AI 协作
  → 掌握了 SubAgents + 文档体系 + CI/CD 集成
```

## 七、术语速查表

| 术语 | 解释 |
