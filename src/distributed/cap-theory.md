# CAP 理论

## 三个核心概念

| 字母 | 概念 | 含义 | 简单理解 |
|------|------|------|---------|
| **C** | Consistency 一致性 | 所有节点同一时刻数据完全一致 | 读写任意节点拿到的数据都一样 |
| **A** | Availability 可用性 | 每个请求都能得到非错误的响应 | 系统随时能响应，哪怕数据不是最新的 |
| **P** | Partition Tolerance 分区容错性 | 节点间网络断开后系统仍能正常运行 | 网络出问题，系统还能继续服务 |

---

## CAP 定理

**三者只能同时满足两个，必须牺牲一个。**

```
      C（一致性）
       /\
      /  \
     /    \
    / CAP  \
   /  三角形 \
  A ————————— P
（可用性）   （分区容错性）

你只能选一条边，放弃对面的顶点。
```

---

## 三种取舍组合

### CP — 牺牲可用性

发生网络分区时为了一致性，**拒绝部分请求**，系统暂时不可用。

```
选一致性 + 分区容错性 → 放弃可用性
```

- **Zookeeper**：Leader 挂掉后重新选举期间，集群不对外服务
- **Etcd**：同样优先一致性

### AP — 牺牲一致性

发生网络分区时保证可用，**可能读到旧数据**。

```
选可用性 + 分区容错性 → 放弃一致性（强一致性）
```

- **Eureka**：优先保证服务可用，各节点数据可能不一致
- **Cassandra**：最终一致性，优先可用

### CA — 牺牲分区容错性

```
选一致性 + 可用性 → 放弃分区容错性
```

- 在**分布式系统中不存**在网络分区的情况才能有 CA
- 分布式系统中 P 无法避免（网络不可靠），所以 **CA 在分布式里不存在**
- 单机系统（如单机 MySQL）可以做到 CA

---

## 现实中的选择

```
关键是"当网络分区发生时，你选 C 还是选 A？"

发生了网络分区 → P 已经被迫接受
  接下来只有两个选择：
    选 C → 停止服务，等数据同步完再恢复
    选 A → 继续服务，接受数据可能不一致

不存在"我不选 P"这个选项—网络分区必然会发生。
```

---

## Redis 在 CAP 中的定位

| 模式 | 定位 | 原因 |
|------|------|------|
| 单机 Redis | CA | 没有分布式节点，不存在网络分区问题 |
| Redis Cluster | **AP** | 优先可用性，主从异步复制，切换时可能丢数据 |

---

## 面试这样说

> CAP 定理说的是：一致性、可用性、分区容错性三者只能同时满足两个。在分布式系统中，网络分区无法避免，所以 P 是一定要选的，真正的取舍在于：当网络出问题的时候，你选一致性（CP）还是可用性（AP）。选 CP 就停下来等数据一致再服务，比如 Zookeeper；选 AP 就继续服务但可能数据不一致，比如 Eureka。Redis Cluster 属于 AP 模型。
