## 逐题复盘

### Q3 — 滑动窗口限流（Redis ZSET + Lua）

**问法：** 你用了 Redis + Lua 脚本做滑动窗口，能简单介绍一下怎么做的吗？限流逻辑是什么？用什么数据结构？ZSET 里存什么？score 是什么？value 是什么？还需要存 value 吗？直接 List 做队列行不行？为什么一定要用 ZSET？

**考察点：**
- ZSET 的 score 存时间戳，value 存请求唯一 ID（或直接用时间戳+随机数）
- value 必须有，因为 ZSET member 不可重复，score 相同会覆盖
- 限流逻辑：`ZREMRANGEBYSCORE key 0 (now-window)` 清除过期 → `ZCARD key` 判断是否超限 → 未超限则 `ZADD`
- **为什么不用 List？** List 不具备按 score 范围删除的能力，用 LPUSH + LTRIM 只能做固定窗口；ZSET 的核心优势是 `ZREMRANGEBYSCORE` 能精确删除窗口外的数据，做到真正的**滑动窗口**
- 补充：滑动窗口比固定窗口更平滑，不会在窗口边界出现"双倍流量"问题

### Q4 — 令牌桶算法

**问法：** 除了滑动窗口，其他限流算法了解吗？令牌桶是什么？让你写一个令牌桶怎么做？核心流程？怎么判断令牌够不够？怎么控制并发？

**考察点：**
- 令牌桶核心参数：rate（生成速率）、capacity（桶容量）、currentTokens、lastRefillTime
- 核心流程：先 `refill()`（根据时间差计算新增令牌），再判断 `currentTokens >= required`，够则扣减并放行
- 并发控制：`synchronized` 或 `AtomicLong + CAS` 或 `ReentrantLock`
- 区别：令牌桶允许突发流量（桶里积攒的令牌一次性打出去），漏桶不允突发

### Q5 — Lua 脚本使用限制

**问法：** Lua 脚本在 Redis 中使用有什么限制？

**考察点：**
- **原子性**：Redis 单线程执行 Lua，执行期间不处理其他命令（阻塞风险）
- **脚本要短小精悍**：不能有过长循环、不能有阻塞操作
- **确定性**：不能使用随机数、时间戳等不确定函数（影响主从复制 / AOF）
- **集群限制**：所有操作的 key 必须在同一个 slot（使用 hash tag `{xxx}` 解决）
- **调试困难**：`SCRIPT KILL` 只能杀未写入的脚本
- **lua-time-limit**：默认 5 秒，超时会被打断

### Q6 — Redis 预扣库存 + 异步下单

**问法：** 扣完库存之后给用户返回抢票成功了吗？

**考察点：**
- Redis 扣库存只是**预扣**，返回的是"排队中"而非"抢票成功"
- 真正下单成功的标志：MQ 消费者处理完毕，订单状态落库为"已支付/已确认"
- 为什么这么做？削峰——Redis 扛高并发扣库存，MQ 平滑消费，防 DB 打爆
- 前端轮询或 WebSocket 推送最终结果

### Q7 — Redis 写 ZSET 异常处理

**问法：** 如果 Redis 写 ZSET 时异常了（没响应、请求丢了），订单没写进 ZSET，这订单是不是永远关不了了？

**考察点：**
- 需要有**兜底机制**：
  1. 定时任务扫描 DB 中长时间未支付/未处理的订单，主动关闭
  2. Redis 写失败时重试（最多 N 次），超过重试次数记录日志/告警
  3. 订单表加 `expire_time` 字段，定时任务按 expire_time 关单
- 不能只依赖 Redis，DB 是最终兜底

### Q8 — 多级缓存刷新时间

**问法：** 本地缓存刷新时间是多久？

**考察点：**
- 本地缓存（Caffeine/Guava Cache）通常设 TTL 几秒到几十秒（视业务容忍度）
- 刷新策略：主动刷新（MQ 通知） + 被动过期
- 本地缓存刷新的一致性窗口：取决于 TTL 和刷新机制
- 补充：两级缓存（本地 + Redis）的一致性方案（Canal 监听 binlog 刷新 Redis，Redis 变更通知刷新本地）

### Q9 — 布隆过滤器

**问法：** 能简单说一下布隆过滤器的思想吗？

**考察点：**
- 核心思想：用 k 个哈希函数映射到 m 位 Bitmap，**宁可误判也不漏判**
- 特性：不存在的一定不存在（100% 准确），存在的可能不存在（误判率）
- 应用：穿透缓存/DB 的无效请求、爬虫去重、黑名单
- 不能删除（原因：多位共享）
- 误判率公式：与 m（位数组大小）、k（哈希函数数）、n（元素数量）的关系

### Q10 — Bitmap 的问题

**问法：** 一千亿 UID，用 Bitmap 记录每天是否弹过通知，会有什么风险？

**考察点：**
- 内存计算：1000 亿 bit ≈ 12.5 GB，每天一份不可持续
- **稀疏性问题**：UID 不连续、分布稀疏时，Bitmap 严重浪费空间
- 解决方案：
  1. **分片**：按 UID 取模分片，每天只存当天活跃用户
  2. **RoaringBitmap**：对稀疏数据自动切换存储结构
  3. **布隆过滤器**：如果只需判断"是否弹过"
  4. **Hash 分桶**：hash(uid) % N 作为 Bitmap 下标

### Q11 — HashMap 底层原理

**考察点：**
- JDK 1.8：数组 + 链表 + 红黑树
- put 流程：hash → 找桶 → 桶空直接放 / 桶非空判断是链表还是树 → 尾插法到链表 / 插入红黑树 → 判断是否扩容/树化
- 扩容（resize）：容量翻倍、rehash（`(n-1) & hash` 或 `hash & oldCap == 0` 高位判断）
- 树化阈值 8，退化为链表阈值 6（为什么是 8？泊松分布，概率 < 千万分之一）
- 线程不安全：1.7 头插法死循环、1.8 覆盖丢失
- 对比 ConcurrentHashMap：分段锁 → CAS + synchronized

### Q12~14 — synchronized + Monitor + 锁升级

**Q12：synchronized 怎么实现的？**
- JVM 层面：`monitorenter` / `monitorexit` 指令
- 基于 Monitor（管程）实现

**Q13：Monitor 是什么？计数器、队列放哪里？加锁信息维护在哪？**
- Monitor 是 C++ 对象 `ObjectMonitor`，包含：
  - `_owner`：持有锁的线程
  - `_count`：重入次数
  - `_EntryList`：阻塞等待队列
  - `_WaitSet`：wait 的线程队列
- 加锁信息：维护在**对象头**的 Mark Word 中

**Q14：对象头 & 锁升级**
- Mark Word 结构：hashcode(25) | age(4) | biased_lock(1) | lock(2)
- 锁升级路径：**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**（不可逆降级）
- 轻量级锁加锁：在线程栈帧中创建 Lock Record，CAS 将 Mark Word 替换为指向 Lock Record 的指针
- 轻量级锁解锁：CAS 还原 Mark Word，失败 → 说明有竞争 → 膨胀为重量级锁
