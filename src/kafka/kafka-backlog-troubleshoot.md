# Kafka 消息堆积排查 SOP

> 基于项目实际经验：API 调用日志通过 Kafka 异步采集，多 Pod 共用消费组

---

## 排查总流程

```
发现堆积 → 看监控 → 判断类型 → 对症下药
                │
        ┌───────┼────────┐
        ↓       ↓        ↓
    生产猛    消费弱    Rebalance死循环
```

---

## Step 1：看监控，判断是不是真问题

看两个关键指标：

| 指标 | 含义 | 怎么看 |
|------|------|--------|
| **Lag** | 还未消费的消息数 | Lag 上涨 = 堆积中 |
| **Offset** | 消费者当前消费到的位置 | Offset 不变 = 消费停滞 |

**场景 A：Lag 不怎么变，Offset 一直在走**

```
生产速度 ≈ 消费速度 → 暂时没大问题
→ 如果只是瞬时流量高峰，等生产慢了自然消掉
→ 不需要急着扩容
```

**怎么判断是不是瞬时高峰？** 拉历史消费曲线对比：
- 突然升高，历史曲线平缓 → 瞬时流量，等等就行
- 最近一周持续走高 → 业务增长，需要扩容

**场景 B：Lag 持续稳定增长**

```
生产速度 > 消费速度 → 消费能力不足 → 需要提升
→ 转入 Step 2
```

---

## Step 2：消费能力不足，怎么扩容？

### 情况一：分区数 > 消费者数（最常见）

```
Partition: [P0] [P1] [P2] [P3] [P4] [P5]   ← 6 个分区
Consumer:  [C0]          [C1]                ← 2 个 Pod

P0→C0, P1→C0, P2→C0
P3→C1, P4→C1, P5→C1

C0 消费 3 个分区，C1 消费 3 个分区
→ 多加 Pod，每个消费者分到更少的分区 → 消费能力线性提升
```

**操作：** 直接 `kubectl scale` 加 Pod 数量，最多加到分区数。

### 情况二：分区数 == 消费者数

```
Partition: [P0] [P1] [P2]   ← 3 个分区
Consumer:  [C0] [C1] [C2]   ← 3 个 Pod，各消费 1 个

再加 Pod → C3 无事可做（一个分区最多一个消费者消费）
→ 必须先加分区，才能加消费者
```

**操作顺序：**
```
1. kafka-topics.sh --alter --partitions N    ← 先扩分区（只能增不能减！）
2. kubectl scale --replicas=M                ← 再加 Pod
```

> **设计经验：** 分区数通常要大于预期消费者数，预留扩容空间。比如预期最多 6 个 Pod，分区数设 12。

## Step 3：最坑的情况 — Rebalance 死循环

**现象：** Offset 几乎不动，Lag 飞涨，监控看消费组频繁 Rebalance。

**根因：消费者处理消息超时，未及时 poll 下一批 → Broker 以为消费者挂了 → 踢出消费组 → 消费者重新加入 → 又超时 → 又被踢 → 死循环**

### 典型触发场景

```
poll(500条消息) → 逐条处理
  ├→ 消息1: 调三方接口 → 3s
  ├→ 消息2: 调三方接口 → 3s
  ├→ ...
  └→ 消息500: 调三方接口 → 3s

总耗时 = 500 × 3s = 1500s
max.poll.interval.ms = 300s

1500s > 300s → Broker 认为消费者死了 → 触发 Rebalance
→ 所有消费者停止消费，重新分配分区
→ 分配完继续消费 → 又超时 → 又 Rebalance → 死循环
```

### 根因定位

**本质：`max.poll.records × 单条平均耗时 > max.poll.interval.ms`**

常见原因：
1. 消费逻辑里调了慢的三方接口，没设超时
2. 消费者本地做了重试，但没设上限
3. 消息处理异常没 catch，导致线程卡死

### 解决

**治标（先让消费恢复）：**
- 调小 `max.poll.records`：500 → 100 → 50
- 调大 `max.poll.interval.ms`：300s → 600s

```properties
# 关键判断公式
max.poll.records × 单条耗时 < max.poll.interval.ms
```

**治本（修代码）：**
- 三方接口调用必须设超时 + try-catch
- 消费失败的消息做异步重试（打回死信队列 / 单独 topic），不阻塞主消费
- 如果消息处理本身就慢 → 考虑批量处理优化

## 面试话术

> "Kafka 消息堆积排查三个方向：
>
> 首先看 Lag 和 Offset——Offset 正常走、Lag 不大，说明生产和消费基本持平，瞬时高峰等一下就好。
>
> 如果 Lag 持续增长，说明消费能力不足。先看分区数和消费者数：分区 > 消费者就加 Pod；分区 == 消费者必须先扩分区再加 Pod。所以设计时分区数要大于预期消费者数。
>
> 最坑的是 Rebalance 死循环，根因公式是 `poll.records × 单条耗时 > poll.interval.ms`。典型场景是消费逻辑里调了三方接口没设超时。修代码设超时 + try-catch，调小 poll.records 临时止血。"
