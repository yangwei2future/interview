# 网关压力测试完整方案（JMeter）

## 1. 测试目标
- 目标A：评估网关“纯承载能力”（尽量剥离后端业务耗时）
- 目标B：评估网关在“真实鉴权链路（Token Filter）”下的稳定容量
- 输出口径：在满足 SLO 门槛（P95、错误率、资源水位）下的最大稳定 RPS

## 2. 容量判定标准（建议）
- P95 <= 50ms
- 错误率 <= 0.1%
- 网关 CPU 持续 <= 70%
- 无持续性连接池耗尽、线程池排队爆发、GC 明显抖动

## 3. 测试场景设计（必须对照）
- S1：网关 -> 极简下游服务（关闭 Token Filter）
  - 用途：测网关理论上限（过滤器最小链路）
- S2：网关 -> 极简下游服务（开启 Token Filter，使用压测专用有效 Token）
  - 用途：测真实鉴权开销下的容量
- S3（可选）：网关 -> 真实下游服务
  - 用途：验证与业务真实链路的差异

## 4. 环境与变量控制
- 网关、压测机、下游服务分机部署（禁止同机压测）
- 网关配置冻结：线程池、连接池、JVM 参数固定
- 极简下游服务固定返回 200 + 小 JSON，不查库、不外呼
- 日志级别控制在 INFO，保留指标日志，避免 DEBUG 影响性能
- NTP 时间同步，便于监控对齐

## 5. Token Filter 压测策略
- 推荐：使用“压测专用 Token”（长有效期、固定权限）
- JMeter 统一加请求头：`Authorization: Bearer <token>`
- 如需测纯极限，可在压测环境加“受控绕过开关”：
  - 仅内网来源 + 白名单路由 + 显式环境变量开启
  - 禁止生产开启
- 建议输出鉴权耗时指标：解析耗时、验签耗时、鉴权依赖耗时

## 6. JMeter 测试计划配置
- Thread Group：采用阶梯加压（推荐并发线程组插件）
- HTTP Request：仅压目标路由（固定 Method/Body）
- HTTP Header Manager：
  - `Authorization: Bearer <token>`
  - `Content-Type: application/json`
  - `Connection: keep-alive`
- CSV Data Set Config（可选）：多 Token 或参数集
- Listener：压测时避免大量 GUI 监听，结果写入 JTL
- Backend Listener（可选）：输出到 Prometheus/InfluxDB

## 7. 执行节奏（标准流程）
1. 预热：5-10 分钟（不计入正式结果）
2. 基线：低并发稳态 10 分钟
3. 阶梯加压：每档 10 分钟（示例：100 -> 200 -> 400 -> 600 -> 800 ...）
4. 每档记录：RPS、P95/P99、错误率、CPU/内存/GC、连接池等待
5. 出现拐点后回退一档，稳态复验 20-30 分钟
6. 全流程重复至少 3 轮，取中位结果

## 8. 关键监控指标
- 请求侧：RPS、平均延迟、P90/P95/P99、超时率、4xx/5xx
- 网关进程：CPU、内存、GC 次数与停顿、线程池队列
- 连接资源：上游连接池活跃数、等待数、超时数、重试数
- 系统侧：网卡吞吐、丢包、上下文切换、TCP 状态
- 鉴权侧：Token Filter 耗时分解与失败率

## 9. 结果报告模板
- 测试目标与口径
- 环境信息（机器规格、版本、配置快照）
- 场景结果汇总（S1/S2/S3）
- 容量结论（满足 SLO 的最大稳定 RPS）
- 拐点根因分析
- 优化建议（按收益优先级）
- 与生产差异说明

## 10. 结论表达示例
在 S2（开启 Token Filter）场景下，当 P95 <= 50ms 且错误率 <= 0.1% 时，网关最大稳定承载为 X RPS；超过 Y RPS 后出现延迟拐点，主要瓶颈为（鉴权耗时/连接池等待/CPU）。

## 11. 常见误区
- 只看平均延迟，不看 P95/P99
- 单次压测直接下结论
- 压测机先打满导致误判
- 下游服务不够“极简”导致结果混入业务耗时
- Token 策略不一致导致场景不可比
